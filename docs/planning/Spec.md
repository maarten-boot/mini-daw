## 1. Scope
A small desktop program that records MIDI and audio input on several tracks at once, with live monitoring and playback of takes. A later phase adds VST3 instruments: their audio output can be recorded live, and recorded MIDI takes can be rendered through them to audio.

- **In scope:** recording, monitoring, playback, VST3 instrument hosting (phase 2), MIDI-to-audio rendering through VST3 (phase 2).
- **Not in v1:** note (MIDI) editing and sound (audio) editing. The design must leave room to add them later.
- **Platforms:** Windows 10 first; Linux and macOS later. Platform-specific code stays behind an abstraction layer.

## 2. Technology
- **SPEC-TECH-01** Language: C++ (C++20), build system CMake.
- **SPEC-TECH-02** Audio I/O: RtAudio. Windows backend WASAPI first. ASIO as an option later; see SPEC-LIC-03.
- **SPEC-TECH-03** MIDI I/O: RtMidi.
- **SPEC-TECH-04** Plugin hosting: Steinberg VST3 SDK, used directly.
- **SPEC-TECH-05** GUI: Dear ImGui on GLFW. Rendering: **Direct3D 11 on Windows**, falling back to WARP (Windows' built-in software renderer) when there is no usable GPU driver, as in VMs without 3D acceleration; OpenGL 3.0 on Linux/macOS. The status line shows which renderer is in use; `MINIDAW_D3D_WARP=1` forces WARP for testing. If no renderer can start, the program shows a message box instead of failing silently. GLFW provides the native window handle that VST3 plugin editors need. On Linux GLFW is built for X11 only for now (works under XWayland); native Wayland comes with P12.
- **SPEC-TECH-06** Only libraries whose licence is compatible with MIT (MIT, BSD, zlib, Boost or similar). See section 6.

## 3. Functional requirements

### 3.1 Devices
- **SPEC-DEV-01** List the available audio input/output devices and MIDI input and output ports.
- **SPEC-DEV-02** The user selects the audio device, sample rate and buffer size. Default 48 kHz.
- **SPEC-DEV-03** Device settings are saved and restored on the next start.
- **SPEC-DEV-02a** Implementation: Settings → Audio devices… chooses input device, output device (each also `(default)` or `(none)`), sample rate (44.1/48/88.2/96 kHz) and buffer size (64–2048 frames). Apply reopens the stream; on failure the previous settings are reopened and the error is shown. All input channels of the input device are opened (up to 32) and stereo output. The window shows the actual rate, buffer size, reported latency, dropouts and a peak level per input channel as text (dBFS).
- **SPEC-DEV-03a** Devices are stored **by name** in `[audio]` of `config.ini` (RtAudio ids are not stable between runs). A saved device that is missing falls back to the system default with a visible note; the saved choice is kept, so it is used again when the device returns.
- **SPEC-DEV-05** A stream only counts as running after the first audio callback has arrived (within 1 s). Otherwise the driver's message is shown as an error. If the audio thread could not get realtime priority (Linux), a warning says so. While running, a watchdog notices when callbacks stop for more than 1 second (driver hang, device gone): an error is shown and logged; when they come back, that is logged too.
- **SPEC-DEV-06** `mini-daw --audio-test <seconds>` opens the configured devices without the GUI and prints the actual settings, peak levels, callback count and dropouts. With `--monitor`, see SPEC-MON-01a.

### 3.2 Tracks and recording
- **SPEC-REC-01** The project has several tracks. Each track is an audio track (fed by one or two audio input channels) or a MIDI track (fed by one MIDI input port and channel, or all channels).
- **SPEC-REC-02** Tracks can be armed for recording. All armed tracks record together, sample-synchronised, when Record is pressed. All takes start in the same audio block and keep the same timeline: audio lost in one take (SPEC-REC-05b) is replaced by silence of the same length, so later audio stays in place and all takes of a recording have the same length.
- **SPEC-REC-03** Audio takes are saved as WAV files, 24-bit PCM at the session sample rate.
- **SPEC-REC-04** MIDI takes are saved as Standard MIDI Files (type 1), with timestamps aligned to the audio timeline.
- **SPEC-REC-05** No data is lost if a recording runs at least 60 minutes. Disk writing happens outside the audio thread.
  - **SPEC-REC-05a** While a take is being recorded, its WAV header is refreshed about once a second, so after a crash or power loss the file is valid and holds the audio up to that point. For power loss the file is also forced to the disk at each refresh (`FlushFileBuffers` / `fsync`). This can be switched off for slow disks with `sync_to_disk = false` in `[recording]` of `config.ini` (default `true`); then only a program crash is covered. A take is always forced to disk when it is closed.
  - **SPEC-REC-05b** If audio is lost anyway (the disk cannot keep up, the disk is full), the program says so: the number of lost frames per take and the disk error are reported, never hidden. Lost frames include audio that could not be buffered and audio that could not be written after a disk error. Lost MIDI messages are shown next to the lost frames while recording. The audio thread buffers at least 4 seconds per take (the buffer is rounded up to a power of two: about 5.5 s at 48 kHz). After a disk error the take stops; its file is cut back to the last complete write and keeps a valid header.
  - **SPEC-REC-05c** A plain WAV file can hold at most 4 GiB (about 8 hours of 24-bit mono or 4 hours of stereo at 48 kHz). A take that reaches this limit stops with a clear message; RF64 for longer takes is a later option.
- **SPEC-REC-01a** Implementation (P6): a track list in the main window. *Add audio track* (input channel, or two channels for stereo) and *Add MIDI track* (MIDI input port and channel 1–16 or All); name editable; remove. The track list is kept in the open project (SPEC-PRJ-01a); without a project only in memory. When the audio stream first runs and the user has not made a track yet, one audio track on inputs 1+2 is added (mono if the device has one input). Tracks cannot be changed while recording. Each track shows its own input level (audio, dBFS) or message count (MIDI); the list of all input levels is folded away under "Input levels" (on the Audio setup tab, SPEC-UI-12). MIDI input ports are opened only for armed MIDI tracks (Windows lets only one program open a port); a port that does not open (unplugged, in use) is tried again about every 2 seconds and right before Record (see SPEC-REC-01b). Without an audio input device *Add audio track* is disabled and a note says why; while no track is armed, a line explains Arm and Record.
- **SPEC-REC-01b** MIDI hot-plug: about every 2 seconds the MIDI input list is read again, so a device plugged in later appears in the track's port list. An armed track whose device goes away shows "DISCONNECTED - waiting for it" and the event is logged and shown under the tracks; when the device returns it is opened again automatically, also during a recording (the take goes on; MIDI played while it was gone, and up to about 2 s after it returns, is missing). The take summary says how often a device was disconnected, and such a take counts as having lost data (`--record-test` exit code 1). RtMidi numbers port names (Windows `"Keys 1"`, ALSA `"Keys:Keys MIDI 1 24:0"`) and the number can change after re-plugging or when another device is removed, so a port is found by its exact name, else by the name without that number if exactly one port has it. Only the kind of number the backend adds is removed (Windows " N", ALSA " C:P"; nothing on other backends), so "Synth 1" never opens "Synth 2". Open ports are checked per name without the number, by count: they stay open while at least as many such ports are present (the system may renumber them). Identical devices: when one of several open devices with the same name goes away, mini-daw cannot tell which one, so it closes all of them, logs it and shows "CLOSED - arm off and on"; they are not reopened automatically (a track must never record the other device without notice). Arm the track off and on (after the recording) to open the port again.
- **SPEC-REC-02a** Each track has an Arm checkbox; the armed state is also shown as text ("armed"), not only by colour (SPEC-UI-07). *Record* (button, or Ctrl+R) starts all armed tracks; *Stop* (button, or Ctrl+R again) ends them. While recording the window shows elapsed time, lost frames and any disk error. Recording needs a running audio stream (it provides the timeline), also for MIDI-only recordings.
- **SPEC-REC-04a** MIDI timestamps: the MIDI input thread stamps each message with a steady clock; the audio callback publishes, once per block, the frame position at the end of the block it just received with the clock time of the callback; a message's position on the audio timeline is the latest pair's frame plus the elapsed clock time × sample rate. The callback time jitters by up to a buffer (the audio thread can be woken late, never early), so it is smoothed first: for an ideal stream "clock time − frame / rate" is constant, and the smallest value of the last 0.5–1 s is used (this also follows drift between the audio and system clocks); the first 0.5 s after a stream start use the raw time (drivers often deliver the first blocks in a burst), and a dropout or a jump of more than 50 ms (or 3 buffers) restarts the smoothing. The driver's input latency is not added yet; T-REC-04 measures the offset. Expected accuracy: about 1 ms between MIDI messages, independent of the buffer size. Time 0 of a MIDI take is the first frame of the audio takes recorded with it; MIDI that arrives before that frame (up to one buffer after pressing Record) is not recorded, so a take can start with a note-off. The end of a MIDI take is the end of the recording's timeline (all frames recorded), also when one audio take stopped early. A MIDI message that cannot be placed on the timeline is counted as lost.
- **SPEC-REC-04b** MIDI file: Standard MIDI File type 1: track 0 holds the tempo and the take name, then one track per MIDI track. Timing is chosen by `midi_timing` in `[recording]`: `ppq` (default; 960 ticks per quarter note at a fixed 120 BPM, 0.52 ms per tick) or `smpte` (25 fps × 40 = 1 ms per tick, no tempo). Recorded: all channel messages (notes, controllers, pitch bend, program change, aftertouch). Not recorded in v1: SysEx and MIDI clock/real-time messages. A track set to one channel records only that channel. Notes still held at Stop get a note-off at the end of the take.
- **SPEC-REC-04c** The MIDI file of a running take is rewritten about once a second (via a temporary file and a rename, with the same `sync_to_disk` rule as audio), so a crash loses at most about the last second of MIDI too. A failed rewrite is retried the next second and only stays an error if the final write fails; if the audio stream stops during a recording, the MIDI files of the last rewrite are kept.
- **SPEC-REC-06** `mini-daw --record-test <seconds> <folder>` (1–3600 s) records input channel 1 (and 2, if the device has it) into a take subfolder of the folder (SPEC-REC-07 naming), without the GUI, and prints frames written, lost frames, clipped samples and dropouts (xruns). From P6 it also records every open MIDI input port (all channels) to a MIDI file in the same take folder, and prints the number of MIDI events per port. Exit code 0 when nothing was lost, 1 when audio or MIDI was lost or an error occurred, 2 for a bad command line (e.g. seconds not a whole number from 1 to 3600).
- **SPEC-REC-07** Recording folder: `folder` in `[recording]` (empty = default: Windows `Documents\mini-daw`, Linux and macOS `~/Music/mini-daw`), changeable in Settings → Recording…, which also has `midi_timing` and `sync_to_disk`. Folder, track and file names may contain any characters the file system allows (stored as UTF-8). In `config.ini`, a folder written without quotes is used as typed (`folder = \\server\takes`); inside quotes `\\` stands for one backslash and `\"` for a quote, except that a final `\"` closes the value (`"D:\Takes\"`). While a project is open, takes go into its `takes/` folder instead (SPEC-PRJ-01a). Each Record press creates a subfolder `take-YYYYMMDD-HHMMSS` with one file per armed track: `NN-<track name>.wav` or `.mid` (NN = track number; characters not allowed in file names are replaced by `_`).
- **SPEC-REC-08** (P16, 2026-11-06; the user chose: start at your playing, armed tracks, files only) **Auto record**: an **Auto record** button beside Record (needs an armed track; not while recording or rendering). While it is on, mini-daw waits; a **part** starts at the first channel message (note, controller, pitch bend, …) from an armed MIDI track's input, or when an armed audio track's input or an armed instrument's sound goes above the threshold (`auto_threshold_db`, default −40 dBFS, −60..−20), and ends after `auto_pause_seconds` (default 5, 1..60) without any, while no note is held and the sustain pedal is up (a held note keeps a quiet part open for at most 60 s). Both are in Settings → Recording… and `[recording]` of `config.ini`. Each part records all armed tracks like Record (MIDI, the instrument's sound, audio inputs), from 1 s before the first playing (not before auto record was switched on) to 1 s after the last; the recorder keeps the last 4 s in memory for this and writes nothing between parts. Each part is its own folder `auto/YYYY-MM-DD HH-MM-SS` in the takes folder (the project's when one is open; `-2` … when the name exists), with the usual file names; the tracks and their takes are not changed (File → Open take folder loads a part). Stopping auto record ends a part that is open. Record is disabled and the tracks cannot be armed or changed while it is on; Play may run (the armed tracks' takes do not play then, and playback does not start a part). The transport area shows "AUTO: WAITING" / "AUTO: RECORDING", the part's length and quiet time, losses (audio frames, MIDI messages) and the last 5 parts (the area scrolls when they do not fit); afterwards the number of parts, the folder and any losses (also in the log). Ctrl+R while it is on says to stop it first. Details (crosscheck #11): only the MIDI channels the armed tracks record count; only messages that start sound (note-on, controllers except pedal-up, pitch bend, program change, pressure) and a loud input start a part, note-offs and pedal-up only keep it going; All Notes Off / All Sound Off (CC 123/120) and an unplugged keyboard release held notes. Auto record goes on while the window is minimised. The recorder remembers the last 4 s: if the playing is noticed late (the program was busy), the part starts 3.5 s back, for the WAV and the MIDI files alike, and the log says how much was cut. Audio lost inside a part (also in its first second) is counted; loss cut off at its end is not. If the audio stream is gone when auto record is stopped, the open part ends where the audio stopped (with an error). If a part folder cannot be made, one error is shown and the next playing tries again. Known limit: blocks skipped because the input's channel count changed (a device change) are not on the timeline, so later part edges shift by them (as for normal takes).

### 3.2a Starting
- **SPEC-RUN-01** (P20, user request 2026-11-09: "block mini-daw from starting 2 times for the same user"; user's choice: bring the first window up) Only one mini-daw window runs per config folder, so per user with the default config (`%APPDATA%\mini-daw`, `~/.config/mini-daw`); another `--config` in another folder is a separate one. The lock is the operating system's lock on `mini-daw.lock` in that folder (Windows `LockFileEx`, elsewhere `flock`), released by the system when mini-daw ends, also after a crash; the file holds the owner's process ID. A second start (double-click, Start menu, `mini-daw` in a terminal) opens no window and does not touch the log: it writes a request (`mini-daw.show`), lets the running one take the foreground (Windows: `AllowSetForegroundWindow`), prints "mini-daw is already running …" (to a terminal, if there is one) and quits with exit code 0. The running mini-daw looks for a request about twice a second (also while minimised): it restores and shows its window, asks for the focus (if the system keeps the focus elsewhere, the taskbar button flashes) and logs it. Command-line runs (`--list-devices`, `--audio-test`, `--record-test`, `--contrast-report`, `--version`) are not blocked. If the lock file cannot be made (a read-only folder), mini-daw starts anyway and logs a warning.

### 3.2b Diagnostics
- **SPEC-LOG-01** A log file `mini-daw.log` in the folder of the config file in use (default Windows `%APPDATA%\mini-daw`, Linux `~/.config/mini-daw`), started fresh at each GUI, `--audio-test` or `--record-test` run; the previous run is kept as `mini-daw.old.log`. Each line: local time with milliseconds, level as text (INFO, WARNING, ERROR) and message. Logged: start, config file and warnings, graphics renderer, the device scan, audio stream opens (settings or error), driver messages, MIDI port opened / disconnected / connected again / failed, changes in the MIDI input list, recording start, take results, recording errors, config save errors, fatal start-up errors. Each line is flushed at once; the file stops growing at 5 MB (with a note). If the previous log cannot be renamed (e.g. another mini-daw has it open), the new run is added to the end of it, after a marked line, so nothing is lost. A disk error during a recording is logged when it appears; "Rescan devices" logs the new device list. View → Log (Ctrl+L) shows the latest 2000 lines of this run, can show only warnings and errors, copies all lines to the clipboard and opens the log folder. The status line shows the number of warnings and errors. Never written from the audio callback (SPEC-NF-01).

### 3.3 Monitoring
- **SPEC-MON-01** Input monitoring can be switched on or off per armed audio track.
- **SPEC-MON-02** Each track shows an input level meter.
- **SPEC-MON-01a** Implementation (P7): each audio track has a Monitor checkbox with its state as text ("on", "off", "on when armed", "no output"). Monitoring sounds only while the track is armed and an output device is open; it can be switched during a recording. A mono track goes to both output sides at full level, a stereo track's first channel to the left and its second to the right; with a mono output device left and right are averaged; a channel used by several monitored tracks is heard once. Gain changes are ramped over one audio block (no clicks). The output is limited to −1..1 (0 dBFS); a sample that is not a number (a driver glitch) becomes silence. A tooltip warns to use headphones (feedback with speakers), and while monitoring is on the window shows the delay of at least two buffers plus the driver's latency. Default off. The audio thread reads the gains from atomics (SPEC-NF-01). `mini-daw --audio-test <seconds> --monitor` monitors the default track (inputs 1+2, or 1) and also prints the output peak.
- **SPEC-MON-02a** Meters: a bar from −60 to 0 dBFS per channel (a stereo track shows two thin bars), with marks at −18 and −6 dBFS and a peak-hold line (1.5 s, then it falls). The bar rises at once and falls at 20 dB/s. Beside it, the level as dBFS text (the highest peak of the last 0.5 s, a higher peak at once) and, after a peak reached full scale (≥ 0.999, about −0.01 dBFS), a CLIP button that stays until clicked or until Record starts. The text and the CLIP button have a fixed width (room for the longest value, and for CLIP also while it is hidden), so nothing to their right moves when the value changes. The audio stream section also shows an output meter, fed with the level before limiting, so its dBFS text shows how far the monitor mix went over 0 dBFS. MIDI tracks show their message count and "receiving" for 0.3 s after a message. Colours: Accent and Text on Control, which `colorPairs()` already checks (SPEC-UI-02a).

### 3.4 Playback / transport
- **SPEC-PLAY-01** Transport controls: Play, Stop, Record, return to start.
- **SPEC-PLAY-02** Recorded audio takes play back in sync on the output device.
- **SPEC-PLAY-03** Recorded MIDI takes play to a MIDI output port, or to the track's VST3 instrument (phase 2).
- **SPEC-PLAY-04** Each track has a volume control and mute/solo buttons.
- **SPEC-PLAY-01a** Implementation (P8): *|< Start* (Home), *Play/Stop* (Space, not while typing), *Record* (Ctrl+R); the state as text (STOPPED / PLAYING / RECORDING) with position and length (mm:ss.t). While stopped a position slider sets where Play and Record start. Stop keeps the position; Play at or after the end starts from the beginning; playback stops by itself after the end of the last take (audio and MIDI, plus the MIDI output delay, so the last MIDI events are sent). Tracks cannot be removed while playing, and no take folder can be opened while recording. Each track plays one take: the one it recorded last, or one opened with File → Open take folder (SPEC-PLAY-06); with a project open, the tracks and their takes are saved in it (SPEC-PRJ-02a).
- **SPEC-PLAY-02a** Audio takes are streamed from disk by a reader thread, about 2 s ahead (0.5 s read before playing starts); the audio callback only takes blocks from lock-free rings (SPEC-NF-01). If the disk is too slow, silence is played and the missing part skipped, so takes stay in sync; it is shown ("frames played as silence"). Readable: WAV PCM 16/24/32-bit and 32-bit float, 1 to 64 channels (more than 2: the first two are played), also a take whose header was not refreshed (crash). A take at another sample rate than the stream is not played (message; no resampling yet). A mono take plays on both sides. Output = playback + monitoring, limited to 0 dBFS; the output meter shows both.
- **SPEC-PLAY-03a** Each MIDI track has a MIDI output port for playback, chosen in its Output column (with Edit and Render, SPEC-VST-05a / -04a); default none (no MIDI is sent until one is chosen). mini-daw's own ports are not offered (they would loop MIDI back in). A sender thread sends the merged events about every 1 ms (Windows: timer resolution raised to 1 ms while playing), delayed by the output latency estimate (SPEC-PLAY-05) so MIDI and audio are heard together. Events before the start position are skipped (no controller chasing yet). Stop releases held notes and sends All Notes Off and sustain off on the channels used. Mute releases a track's held notes and sends no new notes, but its other messages (program change, controllers, pitch bend, sustain) still go out, so the sound is right when it is unmuted; held notes are kept per track, so two tracks on one port and channel do not release each other's notes. Volume scales note velocities. Files from other programs: tempo changes and SMPTE timing are followed.
- **SPEC-PLAY-04a** Volume slider −60 dB (= silent) to +6 dB (Ctrl+click to type), M (mute) and S (solo) per track, also during playback and recording; with any solo active only soloed tracks play; mute wins over solo. Gain changes are ramped over one audio block. Applies to audio and MIDI tracks.
- **SPEC-PLAY-05** Overdub: Record plays the takes of the tracks that are not armed, from the play position, while the armed tracks record on the same timeline. Every new take is placed at the timeline position of its first frame (if that is not known because the recording stopped before its first audio block: at the play position where Record was pressed). Only takes that really play (opened, right sample rate, a MIDI output) make it an overdub. During an overdub it is moved earlier by a latency estimate, so it lines up with what was heard: audio takes by 2 × buffer + the driver's reported stream latency + `latency_correction_ms` (`[recording]`, whole ms, −500..500, default 0, also in Settings → Recording…; raise it if overdubs land late); MIDI takes by 2 × buffer + half the reported latency. This is an estimate; T-PLAY-12 measures it with a loopback.
- **SPEC-PLAY-05a** Overdub is explained where it is used (user test 2026-11-05: it was not found): while not recording, with a track armed and other tracks holding takes that would play (a MIDI take only with an instrument or a MIDI output), a line under the transport says how many tracks Record will play along with; the Arm box's tooltip and the hint above the track table say that tracks that are not armed play along. A linked sound track counts only when it plays its recording and its MIDI track is not armed.
- **SPEC-PLAY-06** File → Open take folder… lists the take folders in the recording folder, newest first, or opens any folder typed in. It replaces the track list with one track per take file: `NN-name.wav` → audio track (input 1, or 1+2 for a stereo file), `NN-name.mid` → MIDI track (no output until chosen), each playing from 0.
- **SPEC-PLAY-07** Timeline of recordings (P17, user's choices 2026-11-07: auto parts and takes; click to play, load onto the tracks; long pauses short with their time). The Timeline tab shows the recordings in the takes folder (the project's when one is open) as blocks in time order: a row for auto record parts (`auto/<date time>`) and a row for Record takes (`take-…`), each block labelled with its start time and length ("21:51 0:08"). The recordings and pauses up to 10 s are drawn to scale (zoom: pixels per second); a longer pause is a short marker with its real length ("+12 min", "+2 h 05 min", "+3 days"). The part or take being recorded grows while it is recorded ("REC"; also before its first file exists, as with a MIDI-only take), and the view follows new recordings (while a recording grows only if the view is at its end, so earlier ones can be looked at). Folders without a .wav or .mid file are left out; a file whose length cannot be read is named in the block's tooltip. Times come from the folder names (local clock time); pauses are computed in real time, so they are right across a daylight-saving change (in the autumn hour that occurs twice the order of recordings in that hour can be off). Click selects (shown by "> " and the selection colour), double-click or **Play it** plays it on its own from its start (its WAV files, and its MIDI files to the MIDI output of the track with that number, if it plays to one; not while recording, allowed while auto record waits); Space or **Stop** stops it, and the transport shows its length; Home plays it again from its start. Files that cannot be played (another sample rate, unreadable) are named under the timeline and in the log. Record and switching Auto record on stop it first: Record then starts at the song's own position, and Auto record does not start the song. When it stops, the song position is where it was before. **Load onto the tracks** (not while recording or rendering): each file "NN-name" becomes the take of track NN if it is of the same kind (.wav audio, .mid MIDI), from frame 0; the tracks keep their instruments and settings; files without such a track get new tracks. The list is read again when the tab opens, when a recording or part ends, and with **Refresh**.

### 3.5 VST3 instruments (phase 2)
- **SPEC-VST-01** Scan the standard VST3 folders (Windows: `C:\Program Files\Common Files\VST3`) and list the instruments found.
- **SPEC-VST-02** An instrument can be loaded on a MIDI track. Live MIDI input drives it, and its audio output is monitored.
- **SPEC-VST-03** The instrument's audio output can be recorded live to a WAV take.
- **SPEC-VST-04** A recorded MIDI take can be rendered through the instrument to a WAV file, offline or in real time. (Done offline, faster than real time — the user's choice for P11; real-time rendering is not planned for now, since recording the instrument live already gives a real-time version.)
- **SPEC-VST-05** The plugin's own editor window can be opened.
- **SPEC-VST-06** The plugin's state (preset) is saved with the project.
- **SPEC-VST-07** (PL2, user's choices 2026-11-08) A track's instrument has a preset menu in mini-daw: the plugin's own programs, the preset files of that plugin, and saving the current sound as a preset of one's own.
- **SPEC-VST-01a** Implementation (P10a): Settings → Instruments (VST3)… lists the standard folders (Windows: Common Files\VST3 and the per-user `%LOCALAPPDATA%\Programs\Common\VST3`; Linux: `~/.vst3`, `/usr/lib/vst3`, `/usr/local/lib/vst3`) and up to 8 folders the user adds (`folder1`…`folder8` in `[instruments]`). Scanning runs on demand (button), one module per frame (the window stays responsive, progress shown); a module's `moduleinfo.json` is used when present (not loaded), else the module is loaded and its factory asked. Results are kept in `plugins.json` next to `config.ini`; unchanged modules are not loaded again. A module that crashes mini-daw during a scan (also its first one) is marked "crashed" (marker file `plugin-scan.inprogress`) and skipped later unless "Also try modules that failed or crashed before" is ticked; failed modules are listed with the reason. On Windows, loading a module never opens a system error dialog (bad image, missing DLL): the load fails with a reason instead. Instruments = audio processor classes with "Instrument" in their subcategories.
- **SPEC-VST-01b** Instrument folders (P19, user request 2026-11-07): the window lists the standard folders ("Always searched") and the added ones ("Added by you"), each added one with a **Remove** button in front of it (takes it off the list; nothing is deleted). A folder is added by typing or pasting it (spaces and quotes around it are removed) and Add folder or Enter, or with **Browse…** (SPEC-UI-14), which adds the chosen folder at once. It is refused with the reason when it does not exist, is not a folder, is the top of a drive or of the file system, is a standard folder, is in the list already (also when spelled otherwise) or 8 are added. It is added with a remark when no `.vst3` is in it, when it holds a standard folder (a Scan then searches all of it), or when it is large: the check looks at no more than 20000 entries so the window never stalls. Adding, refusing and removing are logged; the user is reminded to Scan.
- **SPEC-VST-02a** Implementation (P10b): a MIDI track's output list offers the scanned instruments besides MIDI outputs; choosing one loads it (in mini-daw's process: a crashing plugin takes mini-daw down; takes stay valid, SPEC-NF-03) at the stream rate, 32-bit float, up to 4096 frames per call (larger blocks in parts). Live MIDI from the armed track's port (its channel filter applies) reaches the instrument at the start of the next audio block; during playback the take's MIDI reaches it at its exact sample; notes the playback started are released at Stop, notes played live are released when the track is disarmed (also when the key is still down); if a block has more events than fit (512 per instrument), note-offs are kept first, so no note hangs. Its stereo output is mixed with the track's volume, mute and solo (ramped), before limiting and the output meter. Notes and poly pressure become VST3 note events; controllers, pitch bend, channel pressure and program changes go through the plugin's MIDI mapping (if it has one); when one parameter changes more often in a block than its queue holds, the latest value wins. A plugin's restart request (restartComponent) is logged; when its busses changed or it asks to be reloaded, it is loaded again with its settings (and its editor reopened). Up to 16 instruments. After a sample rate change the instruments are loaded again with their state (not after a buffer size change), and MIDI takes are timed for the new rate.
- **SPEC-VST-03a** Implementation (P11a/b): the sound of a MIDI track's instrument lives on its **linked audio track** ("<MIDI track name> sound"), made right below the MIDI track as soon as an instrument is chosen for it (and loads), so it is visible before recording (user test 2026-11-05); also when an older project's instrument track is recorded or rendered without one. Choosing a MIDI output or none instead removes the linked track again if it holds no take (not while recording or while this track renders); one with a take stays. The linked track has no input, arm or monitor of its own; it has volume, mute and solo. When an armed MIDI track with a loaded instrument is recorded, the take folder gets its `.mid` as before and the instrument's stereo sound, before the track's volume, as the linked track's `NN-<name>.wav` (24-bit, session rate, sample-aligned with the other takes; no audio input device needed); an instrument that is not loaded records no sound (the linked track keeps its take). The WAV is placed like its MIDI take (in an overdub moved earlier by the MIDI latency estimate, as the notes it was made from). A block too long to keep (over 8192 frames) is reported as lost, like any other loss. While recording, an armed instrument track's old linked take does not play (the instrument plays live). **Sound from** (in the linked track's Input column): "instrument" (default) — the instrument plays the MIDI take, the linked track is silent; "this recording" (only when it has a take) — the linked track plays its WAV and the instrument gets no take MIDI (playing live on the armed track still sounds). Muting the MIDI track also silences its linked track; soloing it lets the linked track sound. Removing the MIDI track keeps the linked track as a normal audio track; removing the linked track sets its MIDI track back to "Sound from: instrument". `project.json`: `instrumentOf` on the linked track, `soundFrom` on the MIDI track; a link to a missing track, or a second link, becomes a normal audio track (with a warning); a linked track is never armed or monitored itself.
- **SPEC-VST-04a** Implementation (P11c): **Render** on a MIDI track with an instrument and a take renders the take through a second instance of its instrument (same plugin, its current settings, VST3 offline mode) on a worker thread, faster than real time, while playing goes on; progress in percent and **Cancel** replace the button. Each render makes a new file in the take's folder, `NN-<linked name>-render.wav` or, when that exists, `-render-2.wav`, `-3`, … (the recorded WAV and earlier renders are kept, so a render never touches a file that plays); it holds the take from its frame 0 plus the sound after its end until 0.5 s below −80 dBFS (at most 10 s), and becomes the linked track's take at the MIDI take's position. A cancelled or failed render leaves no file (only its own new file is removed). Render first checks the take and the instrument and only then makes the linked track; the result is kept only if the MIDI track still has the same take. Opening another project or quitting cancels a running render. One render at a time, and not together with a recording (Record waits until the render is done).
- **SPEC-VST-05a** Implementation (P10d, Windows): a MIDI track with a loaded instrument shows an **Edit** button (in front of its output list); it opens the plugin's own editor in a separate window titled "<plugin> - <track> - mini-daw", at the size the plugin asks for, at the display's scale (given to plugins that support scaling, again when the window moves to a display with another scale). The window belongs to the main window (stays above it, minimises with it, no taskbar button of its own); playing and recording go on while it is open. The button then reads **Close**; the window's own close button does the same. The window can be resized only if the plugin allows it, within the plugin's limits; the plugin can resize it itself. Changing or removing the track's instrument, opening another project and quitting close the window first; after a sample rate change (instruments are loaded again) open editors are opened again. A plugin without an editor, or without one for this system, is reported in the Instruments notes and the log. Linux: the button is shown disabled ("Linux later"; X11 editors need a VST3 run loop).
- **SPEC-VST-06a** Implementation (P10e): the instrument (class ID, module path, name, and since PL2 the name of the preset chosen last, for display) and its processor and controller state (base64) are stored per track in `project.json`; the state is taken from the plugin every 5 s and before switching projects or quitting. Opening a project loads the instruments with their state (the module is looked up by class ID in the scan results first, so a moved plugin is still found); a missing or failing plugin is reported and the track keeps its settings.

### 3.6 Project
- **SPEC-VST-07a** Implementation (PL2): a MIDI track with a loaded instrument shows **Presets**, **<** and **>** in its Output column, after Edit (also on Linux, where Edit is not available yet). **Presets** opens a menu: "Track N: <preset>", then **Programs** — the plugin's program list (VST3 `IUnitInfo`: the list of the unit that owns the program-change parameter, the root unit's first; another unit's list only when the plugin has just one; without one, the value names of a list-type program-change parameter; a name the plugin does not give is shown as "Program N"; only the entries the parameter can reach are listed: its steps + 1, or for a continuous parameter the list's size), chosen by setting that parameter (to the processor at its next block, and to the controller, so an open editor follows) — then **Preset files** — every `.vstpreset` of the plugin in the standard folders, `<root>/<vendor>/<plugin name>` (names made safe for a folder): Windows `Documents\VST3 Presets` (the user's), `%APPDATA%\VST3 Presets`, `%PROGRAMDATA%\VST3 Presets`; Linux `~/.vst3/presets`, `/usr/share/vst3/presets`, `/usr/local/share/vst3/presets`; and the bundle's own `Contents/Resources/Presets`; subfolders are shown as "group/name", the user's marked "(mine)", at most 2000 listed and at most 50000 entries searched per folder (each with its own note), the full path as tooltip. Exactly one entry has "> " (SPEC-UI-15): the one chosen last (by its identity, so two entries with the same name stay apart; in this session), else one with the track's preset name, else — nothing chosen in mini-daw yet — the plugin's current program. A file is loaded through the busy message (SPEC-UI-16): its class ID must be 32 hexadecimal characters and this plugin's (else "the preset is for another plugin", logged), then its processor and controller state are set as for a project (SPEC-VST-06a), with the instrument taken out of the audio thread's rack meanwhile (it is silent for that moment), as a project sets the state before the rack has the instrument; a controller that does not take its part is a warning in the log (the sound is set). Programs and files may be chosen while recording, like a knob in the plugin's window; the log says "(while recording)". **Save preset...** opens a window for that instrument (it closes when the instrument is changed or loaded again): name (default: the current preset or the instrument's name; spaces around it removed), the file it will be (`<user folder>/<name>.vstpreset`, the name made safe: characters not allowed in file names become `_`, Windows device names such as CON get a `_` in front, at most 120 bytes), "Replace" when it exists; Save and Enter both only when there is a name and a user folder (else the menu says the folder is not known); written via a temporary file and a rename, errors with the system's reason; logged; the track's preset name is then the file's name, so the menu finds and marks it. **<** / **>** step through programs then files (wrapping round), from the marked entry (from none: the first / the last); the list is read again when it is older than 3 s. When the menu is first opened for a loaded instrument, the log says what it offers ("Presets of X (vendor): N program(s) in list 'L', M preset file(s) in <folders>"), so the user's test shows what a plugin (e.g. Arturia) publishes. The name of the preset chosen last is kept per track (`preset` in the track's `instrument` in `project.json`) for display; the sound itself is in the saved state (SPEC-VST-06a). The `.vstpreset` format is read and written by mini-daw (header "VST3", version 1, 32-character class ID, chunk list; chunks "Comp" and "Cont"), compatible with other hosts.
- **SPEC-PRJ-01** A project is a folder containing a project file (JSON) and the take files.
- **SPEC-PRJ-02** Projects can be saved and reopened.
- **SPEC-PRJ-01a** Implementation (P9): the project folder holds `project.json` and `takes/`; while a project is open, new takes are recorded into `<project>/takes/take-…`. Takes from outside (recorded before the project existed, opened with File → Open take folder, or from another project on Save as) are copied into `takes/imported/<take folder>/`; a file already there is reused only if its content is the same, otherwise the copy gets a free name (`-2`, `-3` …), so an earlier copy is never overwritten. Save as switches to the new folder only when every take could be copied (a take that is gone is only reported). So a project folder is complete on its own and can be moved or backed up as one folder. Copying runs on the GUI thread (a big take makes the window wait). `project.json`: format name and version (1), the stream sample rate, and per track: number, name, kind, input channels / MIDI input and channel, MIDI output, arm, monitor, volume, mute, solo, take (relative to the folder, `/` separators, UTF-8) and its timeline position. Not in the project: audio devices (they belong to the computer, `config.ini`), the play position.
- **SPEC-PRJ-02a** File → New project… (name and parent folder; default `<recording folder>/projects`; starts empty), Open project… (the projects in that folder, or any folder typed in), Recent projects (the last 8), Save project as… (the current tracks into a new folder, takes copied), Close project. Not while recording, and not into a folder inside the open project. Typed folders are made absolute and normal. Every change is saved automatically within about a second (written to `project.json.tmp`, forced to disk and renamed over the old file, so a crash leaves the old or the new file); a save error is shown in the status line and logged, and retried with the next change. The project open when mini-daw closes is reopened at the next start (`last` in `[project]` of `config.ini`; recent ones as `recent1`…`recent8`); if it is gone, a note says so. The title bar and the status line show the project. Opening never crashes: a damaged file (also wrongly typed fields), a newer format version or a missing folder gives a clear error, shown in the status line and the log, and nothing changes; projects in Recent that are gone are marked "(not found)". Bad track fields (wrong types, channels out of range) give warnings and defaults, the rest loads; if repairs were needed, the original file is kept as `project.json.bak` and the repaired state is saved. Missing takes are reported; a different sample rate is noted. Names that are not valid UTF-8 are saved with U+FFFD in place of the bad bytes. Without a project, mini-daw works as before (takes in the recording folder, tracks in memory). Two mini-daw windows on one project are not detected (the last save wins); with the default config a second window is not possible any more (SPEC-RUN-01), with two config folders it still is.

### 3.7 Packaging (Windows)
- **SPEC-PKG-01** Two programs from the same code: `mini-daw.exe` without a console window (double-click, Start menu, installer) and `mini-daw.com`, the console version for the command-line options. In cmd and PowerShell `mini-daw …` runs the `.com` (it comes before `.exe`), so output and exit codes work as before. Given an option that prints anyway, `mini-daw.exe` writes to the terminal it was started from, if there is one (without the exit code); only a stream that has no handle is reopened (so `> file` still works), and `--config <file>` alone opens the window without touching the terminal. Both carry the icon and version information. `tools/check_pe.py` checks this (window/console, icon, version info) and runs as test `pe_check`.
- **SPEC-PKG-02** Installer (NSIS 3, `mini-daw-<version>-setup.exe`, `cmake --build <build> --target installer`; built by CI): installs for the current user without administrator rights into `%LOCALAPPDATA%\Programs\mini-daw` (the folder can be changed), with a Start menu entry, an optional desktop shortcut and an entry in Apps & features (version, publisher, icon, uninstall). The uninstaller removes only what was installed: settings and the log (`%APPDATA%\mini-daw`) and projects and takes stay. Installing over an older version replaces it; an older installer over a newer version asks first (a silent install refuses); an earlier installation in another folder is removed. While mini-daw runs, install and uninstall ask to close it first (a silent one stops, exit code 2, nothing changed). Not signed (no certificate yet): Windows SmartScreen asks before the first run ("More info" → "Run anyway").
- **SPEC-PKG-03** Icon: a white rounded square with a black border, a black waveform and a red record dot (black on white; red on white 5.9:1), drawn by `tools/icon/make_icon.py` into `res/mini-daw.ico` (16–256 px, thicker bars at 32 px and below), `res/mini-daw-256.png` and `src/app/icon_data.hpp` (the window icon on Linux). Windows takes it from the program's icon resource (named `GLFW_ICON`, so the window uses it too).

## 4. UI accessibility requirements (GUI)
- **SPEC-UI-01** Default theme is a white background with black text.
- **SPEC-UI-02** Every foreground/background colour pair meets a WCAG 2.x contrast ratio of at least 4.5:1 (AA).
- **SPEC-UI-03** The user can raise the minimum contrast interactively while the application runs.
- **SPEC-UI-04** The user can set the minimum contrast in a config file.
- **SPEC-UI-05** Contrast presets: AA (4.5:1), AAA (7:1), Max (21:1, pure black/white), plus a custom minimum ratio. A custom value below 4.5:1 is rejected.
- **SPEC-UI-06** When a minimum is active, any colour pair below it is adjusted until it meets that minimum.
- **SPEC-UI-07** Level meters and other status shown by colour also show it another way, such as a text value or pattern.
- **SPEC-UI-02a** Contrast is checked on a fixed list of foreground/background pairs between colour roles (`colorPairs()`). Every ImGui colour slot maps to a role, so no toolkit default escapes the check. Borders, separators, check marks and scrollbar thumbs are held to the same minimum as text (stricter than WCAG's 3:1 for non-text). Disabled controls (PL1) are drawn flat (no fill of their own) and faded only as far as the minimum allows: the fade is the lowest opacity at which every foreground still meets the minimum on every background a disabled control can show (`disabledPairs()`, at least 60 % opacity; AA about 95 %, AAA and above none). Before PL1 ImGui faded them to 60 % at every setting, below the minimum at AAA and Max. `View → Contrast report` and `mini-daw --contrast-report` list every pair with its ratio, the disabled ones as drawn ("…, faded to 95 %").
- **SPEC-UI-03a** Implementation of UI-03: menu View → Contrast (AA, AAA, Max, Custom…, Raise, Lower) and the shortcuts Ctrl+Shift+Up / Ctrl+Shift+Down, which step through AA → AAA → Max. An interactive change is saved to the config file immediately.
- **SPEC-UI-04a** Implementation of UI-04: INI file, key `min_contrast` in section `[ui]`, value `AA`, `AAA`, `Max` or a number from 4.5 to 21. Default location: Windows `%APPDATA%\mini-daw\config.ini`, Linux `~/.config/mini-daw/config.ini`, macOS `~/Library/Application Support/mini-daw/config.ini`; `--config <file>` overrides it. Saving keeps the user's own comments and other lines. An invalid value gives a visible warning and falls back to AA.
- **SPEC-UI-08** Text size is adjustable from 12 to 32 px (default 16 px), as the size at 100 % display scaling; text, spacing and the first window size follow the display's scale (e.g. 24 px at 150 %), also when the window moves to a monitor with other scaling: View → Text size, Ctrl+= / Ctrl+- / Ctrl+0, and `font_size` in `[ui]` of `config.ini`. Uses ImGui's built-in scalable font.
- **SPEC-UI-09** The main window opens at the size and place it had when mini-daw was last closed, and maximised if it was (user request 2026-11-06); on by default, off with `remember = false` in `[window]` of `config.ini`. mini-daw writes the normal (not maximised, not minimised) position and size in screen pixels (`x`, `y`, `width`, `height`, the inside of the window) and `maximized` when it closes normally. At start the saved place is fitted to the screen work area it overlaps most (made smaller if needed and moved inside, the title bar on screen); if less than 100 × 50 pixels of it would be on any screen (a monitor that is gone, or remembering off, or bad values with a warning), the default place and size of SPEC-UI-08 are used. The window stays hidden during the start-up work (devices, last project, instruments) and is shown right before its first frame, maximised in one step if it was (Windows: SetWindowPlacement, keeping the normal place for un-maximising), so no empty or half-sized window is seen (user test 2026-11-06).
- **SPEC-UI-10** The track table does not move when lines come and go (user test 2026-11-06): the transport's position slider and Recording settings button are always shown (disabled when not usable); the lines below them (recording state, overdub, take folder, errors, the last take) share an area of fixed height (7 text lines) that scrolls when they need more; the hint above the track table is always shown. The track table's columns fit their content at fixed widths (never sized from the space left, which made the MIDI port list push the Take column out of the window), with the MIDI output / instrument, Edit and Render in their own **Output** column; when the table is wider than the window it gets a horizontal scrollbar, and #, Arm, Monitor and Name stay in place while it scrolls (PL1). Its height is counted from the rows (one control high) and grows by what the last frame measured beyond that, if a cell is ever taller (logged once).
- **SPEC-UI-11** The main window has tabs (user request 2026-11-07): **Recording** (a short audio status line, transport, tracks), **Timeline** (the transport and the timeline of recordings, SPEC-PLAY-07) and **Audio setup** (SPEC-UI-12). Switching tabs never stops anything: a recording or auto record goes on, and the transport is on the Recording and Timeline tabs.
- **SPEC-UI-12** Audio setup tab and tab order (P18, user's choices 2026-11-07). The **Audio setup** tab holds what is used only to set up: the audio stream (Audio settings…, devices in use, sample rate, buffer, latency, dropouts, output level, input levels, notes such as missing realtime priority) and the device list (audio devices, MIDI inputs and outputs, Rescan). The Recording tab keeps one line: the stream's API, sample rate, buffer and dropouts and the output meter; when the stream is stopped or has stalled, or there are notes, it says so with an **Audio setup** button in front of the text (so a long message cannot push it out of the window) that opens the tab. The tabs can be put in any order by dragging a tab, or in **Settings → Tabs…** (Up / Down per tab, Default order; usable with the keyboard). The order and the tab used last are kept in `config.ini` (`[tabs] order = recording, timeline, audio`, `last = …`; in `order` unknown names are left out with a warning, repeats left out, missing ones added at the end; an unknown `last` becomes `recording` with a warning) and saved when they change; at start the tab used last is shown (no other tab is drawn or saved as the last one meanwhile). In Settings → Tabs… the keyboard focus moves with the tab moved, and to its other button when it reaches the top or bottom. Audio driver messages are all written to the log; in the notes a repeated message is counted ("… (3 times)") and at most 50 notes are kept, the last one then pointing to the log.
- **SPEC-UI-13** Keyboard use (crosscheck #13, 2026-11-07): in every window Tab / Shift+Tab and the arrow keys move between controls (a frame shows the one in focus), Enter presses it, Escape leaves it. Space (Play / Stop) and Home (to the start) stay the transport's keys and never press the control in focus; in a text field Space types a space and Home goes to the start of the text. While a menu or a modal window (the folder browser) is open no shortcut acts (Ctrl+R, Space, Home, Ctrl+L, text size, contrast): nothing happens unseen behind it; there Space presses the control in focus and Escape closes the browser.
- **SPEC-UI-15** State cues (PL1, user feedback 2026-11-03: "sluggish because of lacking visual feedback"; user's choices 2026-11-08): every control shows its state in a way that is not only a colour, so it also works at Max (21:1): **hovered** — a frame in the Accent role (2 px at 16 px text, more with larger text) inside the control, decided from the frame's final hover state (no delay); title bars and scrollbars get none (they are not controls a click acts on); **pressed** — the same frame and a clearly darker fill (ControlActive #A6A6A6, 2:1 from Control; hovered #CCCCCC, 1.3:1); **selected** list entries (devices, inputs, ports, channels, outputs, instruments, Sound from, MIDI timing) — "> " in front and an Accent bar on the left; the **selected tab** — a thick Accent line on top; **disabled** — flat (also a ticked checkbox), with a dashed frame instead of the solid one and faded as in SPEC-UI-02a (a disabled checkbox: a dashed box round its box); also items ImGui disables itself, such as File menu entries while recording (a dashed frame round the menu row); disabled controls get no hover frame. Accent is checked on every background a control or list entry can have, and a disabled but selected list entry's Text, TextDisabled and Border on Selection (`colorPairs()`, `disabledPairs()`). Implementation: Dear ImGui's item hooks (`IMGUI_ENABLE_TEST_ENGINE`, only the hooks: no test engine is linked) tell mini-daw which control is hovered, pressed or disabled, and the frames are drawn at the end of each frame; disabled blocks use `beginDisabled` / `endDisabled` (src/app/state_cues).
- **SPEC-UI-16** Busy message (PL1): a click that starts slow work on the GUI thread — choosing an instrument (loading the plugin), Apply in Settings → Audio devices, opening a project (also from Recent), New project and Save project as (copying takes) — first shows "<what> ..." in a framed box in the middle of the window; the work starts in the next frame, so the message is on screen while the window cannot draw. The log says how long it took ("Loading instrument X: done in 1.20 s"). One at a time: a second request meanwhile is not started and logged as a warning. The instrument is not changed if the track is recording or rendering by then (logged).
- **SPEC-UI-14** Choosing a folder (P19, user request 2026-11-07): every folder field has a **Browse…** button: the instrument folders, File → New project / Save project as (In folder), File → Open project (Folder), Settings → Recording… (Folder) and File → Open take folder… (Folder). It starts in the folder typed in the field (or the nearest existing folder above it), else in a sensible place (the first standard VST3 folder, the projects folder, the recording folder, the takes folder). The chosen folder goes into the field (an instrument folder is added at once; a recording folder takes effect with Apply, as typed ones do). **Windows:** the system's "Select folder" dialog, owned by the main window, shown from a thread of its own so mini-daw keeps running behind it (meters, auto record); if it cannot be made, mini-daw's own browser is used and the reason is logged. **Linux and others:** mini-daw's own folder browser (a modal window): Up, Home, the drives (Windows), "Show hidden folders", a field to type or paste a path (Enter goes there), the folders inside (click to open), **Choose "<name>"** and Cancel (also Escape). Only one chooser is open at a time. Every folder field removes spaces and one pair of quotes around a pasted path and a separator at the end (not that of a root such as `/` or `C:\`). Folder names that are not valid UTF-8 (Linux) are listed, not fatal; a folder that may not be read says so. Closing mini-daw while a folder is being chosen cancels the chooser first (the Windows dialog as with its Cancel button), then mini-daw closes.

## 5. Non-functional requirements
- **SPEC-NF-01** The audio thread never blocks: no locks, memory allocation or file I/O in the audio callback.
- **SPEC-NF-02** Round-trip latency with WASAPI exclusive mode at a 256-sample buffer stays at or below about 20 ms.
- **SPEC-NF-03** A plugin that crashes or misbehaves must not corrupt takes already written to disk.

## 7. Build and CI
- **SPEC-CI-01** Every GitHub Actions step (or other CI action) is pinned to a full commit SHA, with the release tag as a comment, using the latest release that works. Any exception is written down here with the reason. Exceptions so far: none. (Not an action: NSIS for the installer comes from Chocolatey at a pinned version, 3.13.0; the step checks the version makensis reports.)
- **SPEC-CI-02** CI builds and tests on Windows (primary target) and Linux, and runs the licence and pinning check. The Windows and Linux jobs smoke-run the program and publish it as a download (`mini-daw-windows-x64`, `mini-daw-linux-x64`). Runner images are pinned to a named version (`windows-2025`, `ubuntu-24.04`), not `-latest`.
- **SPEC-CI-03** The project can be cross-compiled for Windows from Linux with MinGW-w64 (`cmake/toolchains/mingw-w64.cmake`).
- **SPEC-CI-04** Every fetched library (`cmake/Dependencies.cmake`) is pinned to the full commit hash of its release, with the release as a comment (`GIT_TAG <sha>  # v1.93.0`), using the latest release that builds and passes the tests; `tools/check_licenses.py` fails on a library without a hash and compares the release with `THIRD_PARTY.md`. A hash cannot be moved to other code, a tag can. Not pinnable by hash: the runner images (GitHub updates them weekly; only the OS version can be chosen), Ubuntu packages from `apt-get` (the archive replaces old versions; signed by Ubuntu) and NSIS from Chocolatey (pinned by version; Chocolatey checks the package checksum). Updated 2026-11-07: RtMidi 6.1.0 (its classes moved into `rt::midi`), Dear ImGui v1.93.0, GLFW 3.5.1; RtAudio 6.0.1, nlohmann/json v3.12.0, VST3 SDK v3.8.1_build_84 and Catch2 v3.16.1 are the newest.

## 8. Known limitations
- **Max (21:1):** every background becomes white, so hovered, pressed and selected states can no longer be told apart by colour. Since PL1 (SPEC-UI-15) they are shown by frames, the "> " mark, the tab line and dashed frames instead; a pressed control is told from a hovered one only by the moment of the click.
- **Windows 10 N editions** have no `MFPlat.dll` (used by RtAudio's WASAPI code) unless the Media Feature Pack is installed. The program then does not start.
- **WASAPI exclusive mode:** RtAudio 6.0.1 opens WASAPI in shared mode only. Shared mode converts sample rates automatically (Line In 44.1 kHz + Speakers 48 kHz works), but SPEC-NF-02 (≈20 ms round trip in exclusive mode) cannot be reached this way. Options: measure shared-mode latency first (T-NF-02); then either extend RtAudio, write an own WASAPI exclusive backend, or rely on ASIO (P14).
- **WASAPI under Wine:** RtAudio's WASAPI client fails to start under Wine 10 in this VM ("Unable to initialize capture/render audio client"); the error is now reported (SPEC-DEV-05). Only real Windows tests count for audio.

## 8b. Observations from the first Windows runs (2026-11-01)
- The first GUI start failed on the user's Windows 10 machine: `GLFW error 65542: WGL: The driver does not appear to support OpenGL` (no OpenGL driver, probably a VM). Fixed by switching Windows to Direct3D 11 with WARP fallback (SPEC-TECH-05).
- Input and output devices can have different native sample rates (Line In 44.1 kHz, Speakers 48 kHz on the user's machine). Handled since P4: one session sample rate (SPEC-DEV-02, default 48 kHz); WASAPI shared mode converts, and a warning is shown when the stream runs at a different rate than requested. Still to confirm on the real machine with an active input (T-DEV-07).
